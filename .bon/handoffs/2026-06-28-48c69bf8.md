## For Claudes to come

**When a "hardcoded marketplace name" (or any "hardcoded target") bug spans several tools, the fix is NOT uniform — split by data-flow direction.** The *read/pull* tools (`/batterie:update`, `/batterie:version`) must discover everything installed on *this machine*, across all family marketplaces — so they generalise to registry-driven discovery. The *push* tool (`publish.py`) legitimately stays pinned to the one remote it triggers (`spm1001/batterie`); generalising it too would be a *bug* (you'd pull a private-flavour plugin after triggering the public assemble that doesn't contain it). Audit "this name is hardcoded everywhere" by asking *which direction each tool moves data*, not by find-replacing the literal. (Now in understanding.md's Publish/Update section, with the deliberate-pin rationale.)

**Identify family membership by source-repo, not by content.** The robust signal for "is this marketplace one of ours" is `known_marketplaces.json → source.repo` matching a pattern, not "does it contain our anchor plugin." Source-repo matching survives cherry-picks (a user installs one plugin from a marketplace without the anchor) and plugin renames; content-matching breaks on both.

**A skill's inline `!`python3 << 'PYEOF'`` block is testable without refactoring it out.** Add a one-line env seam (`X = os.environ.get("OVERRIDE") or <real default>`), then a PEP723 test can extract the heredoc block from the SKILL.md and run it against fixtures — testing the *exact* shipped code, like `lint.py` importing `render.py`. The seam defaults to the real path, so production is untouched; the test makes extraction fail loudly if the heredoc format changes (no silent skip). Pattern lives in `tests/test_marketplace_aware.py`.
