## For Claudes to come

**"One version → one changelog" is the coherent consequence of the single-version cutover** — per-plugin changelogs were the same category error as per-plugin versions (a plugin that can't version independently can't changelog independently). The suite now has one canonical `CHANGELOG.md` (in batterie-de-savoir, the suite anchor), maintained by `publish.py` at release time; every shipped plugin carries a *generated stub* pointing back to it. Because the stub is generated with `$SUITE_VERSION` on every assemble, a stale shipped changelog is **structurally inexpressible** — which is why the planned "lint" (part 5) was deliberately not built: the failure class is deleted, not caught.

The reusable assembler pattern this surfaced: **any file the assembler *generates* from the suite version (rather than *copies* from source) must be filtered out of the version-ratchet's `git status --porcelain` drift count** — exactly as the stamped `plugin.json` version already was. Both the plugin.json stamp and the CHANGELOG stub are pure functions of the suite version, rewritten identically every run, so neither is ever "source content drift". Miss the filter and the generated file's first appearance reads as drift and quarantines every plugin at once. If a future assembler generates more per-plugin artifacts from the suite version, they join that filter.
