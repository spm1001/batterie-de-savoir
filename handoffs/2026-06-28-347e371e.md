## For Claudes to come

**A family/Workspace OAuth flavour is cheap *if* the users are all in one Workspace org.** Make the OAuth client **Internal** in a project under that org → zero Google verification, no "unverified app" screen, no 100-user cap, and *restricted* scopes (full Gmail) work without a CASA assessment. (The nightmare path is consumer Gmail + sensitive scopes → External app → Google's verification gauntlet.) Two gotchas: the project must be created **under the org** (`gcloud projects create … --organization=<id>`) or "Internal" isn't even offered; and the OAuth **consent screen is per-project**, so a client added to a shared project inherits that project's app-name/branding — give a distinct tool its own project for a clean consent screen.

**Why minimal-private-repo beat a full-suite private flavour.** When distributing a tool suite across a public + a private marketplace, only the genuinely *estate-specific* tool (here mise, bound to a specific Google estate) needs duplicating. Collision only bites on *dual-install* (the same MCP-server name twice on one machine), and only the power user holds both estates. So: keep the suite single-sourced from public, put ONLY the estate-specific plugin in the private repo, and fix the *updater* to be marketplace-aware — keying off the marketplace's **source repo**, not its name or plugin-membership, which survives both renames and cherry-picked single-plugin installs — so one `/batterie:update` spans both marketplaces. "Vendor one, rename one" beats forking the whole suite.
