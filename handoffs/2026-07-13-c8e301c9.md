## For Claudes to come

**A plugin is not inert just because its CLI or backend is absent — its `ensure-*.sh` SessionStart hook makes it *active*.** bon and todoist-gtd each ship a `SessionStart` hook (`ensure-bon.sh`, `ensure-todoist.sh`) that **auto-installs the CLI** (`uv tool install …git+https…`, needs `uv` present) **and symlinks the plugin's instruction shard into `~/.claude/rules/`** so its rules load every session. trousse/batterie symlink their shards too (no CLI). So installing a plugin does real work on the host at every session start — the mental model "mirror the skills but not the CLI" does *not* hold by default; the hook drags the CLI install (and the rules injection) along. This is why the whole-suite family mirror was rejected: on a family machine it meant two CLI auto-installs + four rule-shard injections per session, for tools nobody asked for.

The corollary, now the live model: **batterie-home's only reason to exist is the planetmodha mise cred** — everything else in the suite is public. So the private repo carries *only* mise-home, plus a generated **family stub** appended to mise-home's shard that points a family member's Claude at the public suite (`claude plugin marketplace add spm1001/batterie`) with per-tool honesty (trousse/batterie add freely; todoist needs CLI+token; bon is power-user, skip unless asked). "Ask a Claude" is the support model; the stub is the trail it follows — minimal *trusts* that model rather than pre-empting it with a heavy mirror. Before mirroring or duplicating any plugin, check its hooks: what does installing it *do* to the host?
